# /final-review

The definition of done is the spec. This review proves each acceptance criterion was built and tested, and that nothing else was. The work is not done until `review.md` says `Verdict: PASS`.

## Hard rules

1. **Review against `Base:` from the index, never `origin/HEAD` or `main`.**
2. **Read-only until step 7.** You do not fix code. Failures become fix tickets that go through /build. Step 6b runs the app; it writes nothing the tree tracks.
3. **Report only failures of the spec, the tests or security, or a bug step 6c reproduced.** No style or "could be cleaner" findings. The one exception is step 5b, whose findings become refactor tickets unless the user declines them.
4. **Never invent a requirement.** A finding no AC or Out of Scope line covers, and that is not a security or step 6c finding, goes under OPEN for the user.
5. **Keep command output short: it stays in context and is re-read every turn.** Pipe test runs through `2>&1 | tail -40` (pytest with `-q`), read files by line range or grep instead of whole, and never dump a full diff or log you can grep.

## Steps

1. **Gate.** The first word of `$ARGUMENTS` is the spec (a second word `AFK`: see step 8); the index is `index.md` in the same folder. Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf gate <spec> --final`. It checks the branch, a clean tree and that every ticket is `done`. If it prints anything, show it and stop. Run `git fetch origin`; set `BASE` to the index's `Base:` and `HEAD=$(git rev-parse HEAD)`.
   **Delta or full.** If any later word of `$ARGUMENTS` is `FULL`, this is a **full** run. Otherwise, if `docs/work/<feature>/review.md` says `Verdict: FAIL` and the sha after `...` on its `Range:` line (`PREV`) is an ancestor of HEAD (`git merge-base --is-ancestor PREV HEAD`), this is a **delta** run: steps 4, 6 and 6b re-judge only the fix work in `PREV..HEAD`. Otherwise it is a **full** run. Steps 2, 3 and 5 always cover the whole branch.
2. **Red commits.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf red <spec>`: every AC, lettered ones like AC7b included, needs a `test(<id>): red` or `test(<id>): guard` commit in `BASE..HEAD`. Each line it prints is a failure.
3. **Full suite.** Run the index's `Test command` once at HEAD. Record pass, or the failing test names.
3b. **Clean-checkout suite.** Build worktrees get env files copied in by `.worktreeinclude`, so a test that leans on a local `.env` or database passes here and fails on a fresh clone. Run `git worktree add --detach <scratchpad>/clean HEAD`, symlink into it each `.worktreeinclude` path that is not an env file (skip any basename starting with `.env`), and run the `Test command` there with every variable those env files set removed (`env -u NAME` for each name), plus each name listed in `~/.claude/checks/clean-suite-env` if it exists (variables a shell profile can export with no env file). A test that passed in step 3 and fails here is a failure: name it and the variable or file it needed. Then `git worktree remove --force <scratchpad>/clean`.
4. **Tests check their AC.** For each AC, read its red or guard commit (`git log "$BASE..HEAD" --format='%h %s' | grep -E "test\(<id>\): (red|guard)$"`, then `git show <sha>`). Answer one question: does this test fail whenever the AC is false? For a guard, also check that the `Mutation:` in its body is a production-code change the AC forbids, and that the AC really was true before its ticket (else the green was skipped). A test that checks something narrower, different, or nothing is a failure. Only the user can waive one: the row keeps `no` or `partly` and its Note starts `Waived <YYYY-MM-DD> (<user>): <reason>`, which `wf check-review` accepts. Never write a waiver the user did not give in this session; in AFK there is none.
   **Copy.** If the range changed a module-level string constant a person or the model reads, run `${CLAUDE_SKILL_DIR}/../build/scripts/mutate-copy --base "$BASE" <those files> -- <the tests covering them, with -x and a `--deselect <file>` for each snapshot and golden test file>` and paste its output into `review.md`. A `SURVIVED` sentence that states a rule an AC carries (an ask, a price, a limit, a never) fails that AC; any other `SURVIVED` line is listed, not failed.
   **Delta:** re-judge only an AC that (a) has a red or guard commit in `PREV..HEAD`, (b) has its test file in `git diff --name-only PREV HEAD`, or (c) is delivered by a ticket whose `Files` include a file in that diff. Copy every other AC's row from the previous `review.md`, noting `carried from <PREV short sha>`. If unsure whether an AC is affected, re-judge it.
5. **Out of Scope.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf scope <index>`: it lists changed files no ticket planned to touch. Read those diffs first. Then, for each Out of Scope line in the spec, check the relevant diff. Anything built that the line excludes is a failure.
5b. **Structure.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf size <index>`: each line is a file the branch pushed past 1000 lines or grew by 100+ while already over. Then read the branch diff (delta: `PREV..HEAD`) for: a near-duplicate of a helper that already exists (name its path), logic in the wrong layer per the project's CLAUDE.md, and a feature-specific branch added into a shared flow that its own module would keep out. At most 5 findings, each with the smaller structure that removes it, and only ones you would defend. No naming, formatting or taste. These go under `## Structure` in `review.md`; each one fails the verdict and becomes a refactor ticket in step 8. A `wf size` line alone is not a finding: record it, and raise it only if you can name the split. Never re-raise a finding a previous `review.md` marks `declined`.
6. **Security.** Follow `references/security.md` with `<BASE>` filled in. Then name the one fact the change is safe because of (e.g. "every new route resolves `account_id` before reading user data"), and prove it with a script or test that runs the real code, kept in the scratchpad, not the repo. Write the fact, the command and its output into `review.md`. If the proof fails, that is a security finding. If it cannot be proven, write `unproven` and put it under OPEN.
   **Delta:** fill `<BASE>` with `PREV`, and add to the finder prompt: "Earlier commits were already reviewed. For every function this diff changes, open each of its callers anywhere in the branch and check the change does not make that caller unsafe." Re-run the previous review's proof command at HEAD instead of writing a new one, unless the fix diff changes the fact it proves.
6b. **Verify.** If the repo has `.claude/skills/verify/SKILL.md`, read it and follow it for each observable AC: one whose Then can be checked from outside the code, the way a user or client meets it (a screen, a reply or error a client receives, a message, a file, a status code). Not observable: a Then about tests, code structure, or a figure the review computes from source; list each with that reason. Give the skill its AC ids and texts and `BASE`. Record one result per observable AC:
   - `pass` or `fail`, with the skill's evidence block. A fail fails that AC (step 8).
   - `unreachable`, with the skill rule that excludes it (a paid call, an injected fault, a real sign-in). Its test stands; the verdict ignores it.
   - `not run`, with the skill's own output, when the skill stopped before checking (refused, did not start, its instrument check failed). It goes under OPEN.
   Done when every AC has a row and the skill's stop step reported nothing left running and `git status --short` is unchanged. Note the minutes the step took. No skill: write `not run: no verify skill` and go on.
   **A branch that changes its own check.** If `git diff --name-only "$BASE"...HEAD -- .claude/skills/verify/` lists any file, write those files as the first line under `## Verify` and add an OPEN line naming them: the user decides whether the changed check can be trusted.
   **Delta:** verify only the ACs step 4 re-judges; copy every other row from the previous `review.md`, noting `carried from <PREV short sha>`.
   **AFK:** run it as above; the skill's hard rules, not tool permissions, keep it local and free.
6c. **Behaviour.** Follow `references/behaviour.md`. Each finding goes under `## Behaviour` in `review.md` with money or common, its probe and output, and fails the verdict. Each note goes under `### Notes` there as one line.
7. **Write** `docs/work/<feature>/review.md` from `assets/review-template.md`. `Verdict: PASS` only if steps 2-6 (3b, 5b, 6b and 6c included) found nothing and OPEN is empty. Structure findings marked `declined` and behaviour notes do not count. Verify rows marked `unreachable` or not observable, and `not run: no verify skill`, do not count. Then run `${CLAUDE_SKILL_DIR}/../build/scripts/wf check-review docs/work/<feature>/review.md` and apply the `Fix:` on every line it prints, at most 2 passes; a line still printed after that goes under OPEN with the verdict FAIL.
8. **On FAIL.** Build the fix ticket list:
   - an AC failure: an `F<nn>` ticket delivering that AC
   - a verify fail: an `F<nn>` ticket delivering that AC, whose Fixes cites the `## Verify` row and whose Tests block fails on the behaviour that evidence shows
   - out-of-scope code: an `F<nn>` removal ticket (Delivers "none")
   - a clean-checkout failure: an `F<nn>` ticket making that test pass with no env file (Delivers "none (test isolation)")
   - a security or behaviour finding: a new AC under the story it belongs to, worded as Given/When/Then, plus an `F<nn>` ticket delivering it
   - a structure finding: an `F<nn>` refactor ticket (Delivers "none (refactor: no behaviour changes, existing tests stay green)"), whose Files are the duplicate sites plus the file that gets the shared helper
   **Not AFK:** write the AC, verify, removal and clean-checkout tickets without asking, and show the user the list. Ask only about (a) each new AC's wording and (b) each structure ticket: build or decline. Log each answer with `${CLAUDE_SKILL_DIR}/../build/scripts/wf ruling <index> "final-review (<user>): <ruling>; pick: <your recommendation>; chose: <their answer, or \"pick\">"`. A declined structure finding is marked `declined` in `review.md`; if nothing else failed, flip the verdict to PASS and go to step 9.
   **AFK:** never call AskUserQuestion. If OPEN is not empty, commit `review.md` and stop: those are the user's. Otherwise approve the list yourself and log each new AC with `${CLAUDE_SKILL_DIR}/../build/scripts/wf ruling <index> "final-review (afk): added <AC id>, <why>"`.
   Then: add any new ACs to the spec, write each `tickets/F<nn>-<slug>.md` from `assets/fix-ticket-template.md`, append them to the index as `todo`, and commit `docs(review): <feature> fix tickets`. Pick the route and say which in the commit body. **Test-only** (not AFK, and every fix ticket written this round lists only `test:` lines under Files): tell the user `/clear`, then the prompt in `references/test-only-fix.md` with the paths filled in. **Otherwise:** `/clear`, `/build <index path>`, then `/final-review` again.
9. **On PASS.** Run `wf check-review` as in step 7 (step 8 can flip the verdict after it ran), then commit `review.md` (`docs(review): <feature> pass`). Tell the user it is ready for their manual check (the spec's Manual check section) and a PR against `Base:`.
