# /final-review

The definition of done is the spec. This review proves each acceptance criterion was built and tested, and that nothing else was. The work is not done until `review.md` says `Verdict: PASS`.

## Hard rules

1. **Review against `Base:` from the index, never `origin/HEAD` or `main`.**
2. **Read-only until step 7.** You do not fix code. Failures become fix tickets that go through /build. Step 6b runs the app; it writes nothing the tree tracks.
3. **Report only failures of the spec, the tests or security, or a bug step 6c reproduced.** No style or "could be cleaner" findings. The one exception is step 5b, whose findings become refactor tickets unless step 8 declines them.
4. **Never invent a requirement.** A finding no AC or Out of Scope line covers, and that is not a security or step 6c finding, goes under OPEN for step 8.
5. **Keep command output short: it stays in context and is re-read every turn.** Pipe test runs through `2>&1 | tail -40` (pytest with `-q`), read files by line range or grep instead of whole, and never dump a full diff or log you can grep.
6. **Fable decides; the user hears only escalations.** Every question step 8 settles goes through `${CLAUDE_SKILL_DIR}/../build/references/decide.md` (`model: "fable"`).

## Steps

1. **Gate.** The first word of `$ARGUMENTS` is the spec (a second word `AFK`: see step 8); the index is `index.md` in the same folder. Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf gate <spec> --final`. It checks the branch, a clean tree and that every ticket is `done`. If it prints anything, show it and stop. Run `git fetch origin`; set `BASE` to the index's `Base:` and `HEAD=$(git rev-parse HEAD)`.
   **Delta or full.** If any later word of `$ARGUMENTS` is `FULL`, this is a **full** run. Otherwise, if `docs/work/<feature>/review.md` says `Verdict: FAIL` and the sha after `...` on its `Range:` line (`PREV`) is an ancestor of HEAD (`git merge-base --is-ancestor PREV HEAD`), this is a **delta** run: steps 4, 6 and 6b re-judge only the fix work in `PREV..HEAD`. Otherwise it is a **full** run. Step 2's suites, step 3 and step 5 always cover the whole branch.
2. **Start the parallel work.** Right after the gate, before anything else:
   - Dispatch the security finder (step 6, `references/security.md` step 1) and the behaviour finder (step 6c, `references/behaviour.md`).
   - Run `${CLAUDE_SKILL_DIR}/../build/scripts/review-lanes <index> <BASE>` (delta: `<PREV>` for `<BASE>`) with `run_in_background`. It runs the full suite and the clean-checkout suite at the same time and removes its own copies. Build worktrees get env files copied in by `.worktreeinclude`, so the clean lane runs the `Test command` in a fresh worktree with no env file and every variable they set removed.
   - While those run, do your own steps 3 to 5b.
   When review-lanes exits, copy each lane's `LANE` header and indented body into `review.md`'s Full suite section. A `FAIL` lane is a failure; a clean lane that fails where the full lane passed names the test and the variables on its `unset=` list it may need. Exit 2 means it could not start: apply the `Fix:` it printed and run it again.
   Join order: the review-lanes exit comes before step 6b, which runs in the review's own tree. Both finders' reports come before the security coverage check, filters and proof (step 6), then the behaviour sort (step 6c), then step 7 and step 8.
3. **Red commits.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf red <spec>`: every AC, lettered ones like AC7b included, needs a `test(<id>): red` or `test(<id>): guard` commit in `BASE..HEAD`. Each line it prints is a failure.
4. **Tests check their AC.** For each AC, read its red or guard commit (`git log "$BASE..HEAD" --format='%h %s' | grep -E "test\(<id>\): (red|guard)$"`, then `git show <sha>`). Answer one question: does this test fail whenever the AC is false? For a guard, its commit body has a fenced diff under `Mutation:`: judge the guard by that patch. Check that the patch is a production-code change the AC forbids, and that the AC really was true before its ticket (else the green was skipped). A test that checks something narrower, different, or nothing is a failure. Grade the row `yes` or `no`, never `partly`, and no row is waived. `no` only after review-lanes has exited: make a production change that makes the AC false, see the AC's tests still pass, save it with `git diff -- <the production files you changed> > docs/work/<feature>/mutations/<AC id>.diff`, restore the file, and start the Note `Mutation: mutations/<AC id>.diff; <test command>`. A change to wording only is never a `no`. If you cannot make such a change, the row is `yes`.
   **Copy.** The wording check is review-lanes' `LANE wording` block from step 2: it runs mutate-copy on the Python files changed against `BASE`, in its own copy of the branch with the include paths linked in. Paste that block into `review.md`. On `COULD-NOT-RUN`, re-run `${CLAUDE_SKILL_DIR}/../build/scripts/review-lanes <index> <BASE> --only wording --wording-tests "<the tests covering those files, with -x and a --deselect <file> for each snapshot and golden test file>"`. Never run mutate-copy in the review's own tree: it edits files in place. A `SURVIVED` sentence that states a rule an AC carries (an ask, a price, a limit, a never) fails that AC; any other `SURVIVED` line is listed, not failed.
   **Delta:** re-judge only an AC that (a) has a red or guard commit in `PREV..HEAD`, (b) has its test file in `git diff --name-only PREV HEAD`, or (c) is delivered by a ticket whose `Files` include a file in that diff. Copy every other AC's row from the previous `review.md`, noting `carried from <PREV short sha>`; a row that says `partly` is re-judged, not copied. If unsure whether an AC is affected, re-judge it.
5. **Out of Scope.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf scope <index>`: it lists changed files no ticket planned to touch. Read those diffs first. Then, for each Out of Scope line in the spec, check the relevant diff. Anything built that the line excludes is a failure.
5b. **Structure.** Run `${CLAUDE_SKILL_DIR}/../build/scripts/wf size <index>`: each line is a file the branch pushed past 1000 lines or grew by 100+ while already over. Then read the branch diff (delta: `PREV..HEAD`) for: a near-duplicate of a helper that already exists (name its path), logic in the wrong layer per the project's CLAUDE.md, and a feature-specific branch added into a shared flow that its own module would keep out. At most 5 findings, each with the smaller structure that removes it, and only ones you would defend. No naming, formatting or taste. These go under `## Structure` in `review.md`; each one fails the verdict and becomes a refactor ticket in step 8. A `wf size` line alone is not a finding: record it, and raise it only if you can name the split. Never re-raise a finding a previous `review.md` marks `declined`.
6. **Security.** Follow `references/security.md` with `<BASE>` filled in; its finder is already running from step 2. Then name the one fact the change is safe because of (e.g. "every new route resolves `account_id` before reading user data"), and prove it with a script or test that runs the real code, kept in the scratchpad, not the repo. Write the fact, the command and its output into `review.md`. If the proof fails, that is a security finding. If it cannot be proven, write `unproven`: that is a security finding too, and step 8's new AC states the fact so its fix ticket's test proves it.
   **Delta:** fill `<BASE>` with `PREV`, and add to the finder prompt: "Earlier commits were already reviewed. For every function this diff changes, open each of its callers anywhere in the branch and check the change does not make that caller unsafe." Re-run the previous review's proof command at HEAD instead of writing a new one, unless the fix diff changes the fact it proves.
6b. **Verify.** From the repo root, run `${CLAUDE_SKILL_DIR}/../build/scripts/wf verify-skill`. It prints the verify skill's path, `none`, or (exit 1) one `not run: verify skill missing: ...` line. Exit 1: write that line as the only row under `## Verify`, add it under OPEN, and the verdict is FAIL; the user decides (an escalation in decide.md). A path: read that file (it may sit outside the repo; where it says `${CLAUDE_SKILL_DIR}`, use the folder holding that file) and follow it for each observable AC: one whose Then can be checked from outside the code, the way a user or client meets it (a screen, a reply or error a client receives, a message, a file, a status code). Not observable: a Then about tests, code structure, or a figure the review computes from source; list each with that reason. Give the skill its AC ids and texts and `BASE`. Record one result per observable AC:
   - `pass` or `fail`, with the skill's evidence block. A fail fails that AC (step 8).
   - `unreachable`, with the skill rule that excludes it (a paid call, an injected fault, a real sign-in). Its test stands; the verdict ignores it.
   - `not run`, with the skill's own output, when the skill stopped before checking (refused, did not start, its instrument check failed). It goes under OPEN.
   Done when every AC has a row and the skill's stop step reported nothing left running and `git status --short` is unchanged. Note the minutes the step took. No skill (`none`): write `not run: no verify skill` and go on.
   **A branch that changes its own check.** If `git diff --name-only "$BASE"...HEAD -- .claude/skills/verify/` lists any file, write those files as the first line under `## Verify` and add an OPEN line naming them: the user decides whether the changed check can be trusted (an escalation in decide.md).
   **Delta:** verify only the ACs step 4 re-judges; copy every other row from the previous `review.md`, noting `carried from <PREV short sha>`.
   **AFK:** run it as above; the skill's hard rules, not tool permissions, keep it local and free.
6c. **Behaviour.** Follow `references/behaviour.md`; its finder is already running from step 2. Each finding goes under `## Behaviour` in `review.md` with money or common, its probe and output, and fails the verdict. Each note goes under `### Notes` there as one line.
7. **Write** `docs/work/<feature>/review.md` from `assets/review-template.md`. `Verdict: PASS` only if steps 2-6 (both suites, 5b, 6b and 6c included) found nothing and OPEN is empty. Structure findings marked `declined` and behaviour notes do not count. Verify rows marked `unreachable` or not observable, and `not run: no verify skill`, do not count; `not run: verify skill missing: ...` counts. Under `## Check warnings`, grade every line of `docs/work/<feature>/check-warnings.log`: a SURVIVED sentence that states a rule a delivered AC carries is `real`; any other line is `false alarm`. A `real` line that a ticket the index beside the spec records `done` already fixed is graded `real: <reason> (fixed in <ticket id>)` and changes nothing; any other `real` line fails the verdict; a `false alarm` changes nothing. Then run `${CLAUDE_SKILL_DIR}/../build/scripts/check-mutation docs/work/<feature>/review.md` (it edits the tree in place, so review-lanes must have exited) and regrade to `yes` every row it prints, dropping its fix ticket and re-setting the Verdict; exit 2: apply its `Fix:`. Then run `${CLAUDE_SKILL_DIR}/../build/scripts/wf check-review docs/work/<feature>/review.md` and apply the `Fix:` on every line it prints, at most 2 passes; a line still printed after that goes under OPEN with the verdict FAIL.
8. **On FAIL.** Build the fix ticket list:
   - an AC failure: an `F<nn>` ticket delivering that AC
   - a verify fail: an `F<nn>` ticket delivering that AC, whose Fixes cites the `## Verify` row and whose Tests block fails on the behaviour that evidence shows
   - out-of-scope code: an `F<nn>` removal ticket (Delivers "none")
   - a clean-checkout failure: an `F<nn>` ticket making that test pass with no env file (Delivers "none (test isolation)")
   - a security or behaviour finding: a new AC under the story it belongs to, worded as Given/When/Then, plus an `F<nn>` ticket delivering it
   - a `real` check warning not already fixed: an `F<nn>` ticket written in this round, whose id ends that line's row in `## Check warnings` as `(F<nn>)`; one already fixed ends `(fixed in <ticket id>)` and needs no ticket
   - a structure finding: an `F<nn>` refactor ticket (Delivers "none (refactor: no behaviour changes, existing tests stay green)"), whose Files are the duplicate sites plus the file that gets the shared helper
   Write the AC, verify, removal and clean-checkout tickets without asking. Then send decide.md, in one dispatch, (a) each OPEN item with its probe and output (it usually ends as a new AC and fix ticket, an Out of Scope line plus a `TODOS.md` entry, or no change because it does not happen); (b) each new AC's wording; (c) each structure ticket: build or decline. Escalated items stay under OPEN. Every other item leaves OPEN: write its decision on its line in the section it came from, ending `Decided (fable): <decision>`, and log it as `${CLAUDE_SKILL_DIR}/../build/scripts/wf ruling <index> "final-review (fable): <item>; decided: <decision>; why: <why>"`. An Out of Scope decision goes into the spec, with its `TODOS.md` entry, in the same commit as `review.md` (the fix tickets commit below, or step 9's). A declined structure finding is marked `declined` in `review.md`. If nothing else failed and OPEN is now empty, flip the verdict to PASS and go to step 9.
   **Escalations:** not AFK, ask them as decide.md says. AFK, AskUserQuestion is blocked: if OPEN is not empty, commit `review.md` and stop, because those items are the user's.
   Then: add any new ACs to the spec (an AC a Fable decision added gets its own commit and goes last, as decide.md says), write each `tickets/F<nn>-<slug>.md` from `assets/fix-ticket-template.md`, append them to the index as `todo`, and commit `docs(review): <feature> fix tickets`. Pick the route and say which in the commit body. **Test-only** (not AFK, and every fix ticket written this round lists only `test:` lines under Files): tell the user `/clear`, then the prompt in `references/test-only-fix.md` with the paths filled in. **Otherwise:** `/clear`, `/build <index path>`, then `/final-review` again.
9. **On PASS.** Run `wf check-review` as in step 7 (step 8 can flip the verdict after it ran), then commit `review.md`, plus the spec and `TODOS.md` if step 8 changed them (`docs(review): <feature> pass`). Tell the user it is ready for their manual check (the spec's Manual check section) and a PR against `Base:`.
